# طراحی مرحله اول Retail ERP

## 1. هدف

این مرحله نخستین نسخه کاملاً عملیاتی Retail ERP را می‌سازد. مبنای تجربه کاربری، فروشگاه مواد غذایی و سوپرمارکت است؛ اما مرزهای فنی طوری طراحی می‌شوند که صنف‌های دیگر بدون بازنویسی هسته اضافه شوند. عنوان «آزمایشی» فقط به معنی اجرای کنترل‌شده کنار سیستم فعلی است؛ قابلیت‌های داخل محدوده باید واقعی، پایدار و قابل استفاده با داده و پول واقعی باشند.

خروجی این مرحله باید یک برنامه دسکتاپ فارسی و راست‌به‌چپ باشد که کاربر غیر‌فنی بتواند آن را راه‌اندازی کند، کالا و موجودی اولیه بسازد، مشتری ثبت کند، فروش نقدی انجام دهد، پرداخت را ثبت کند و رسید چاپ یا پیش‌نمایش کند.

سند `retail_erp_MASTER_PRODUCT_DESIGN_FINAL_v4_CODEX_SOURCE_OF_TRUTH.md` مرجع نیازمندی‌های محصول است. این سند فقط محدوده و تصمیم‌های اجرایی مرحله اول را دقیق می‌کند و چیزی خلاف مرجع اصلی اضافه نمی‌کند.

## 2. روش تحویل

پروژه با روش «هسته ماژولار + مسیر کامل فروش» ساخته می‌شود:

1. ابتدا زیرساخت مشترک و مرز ماژول‌ها ایجاد می‌شود.
2. سپس یک مسیر واقعی از تعریف کالا تا ثبت فروش و چاپ رسید کامل می‌شود.
3. هر بخش قبل از رفتن به بخش بعدی تست خودکار، تست یکپارچگی و بررسی تجربه کاربری دارد.
4. قابلیت‌هایی که متعلق به فازهای آینده هستند فقط Contract یا نقطه اتصال خواهند داشت و منطق ناقص و نمایشی برای آن‌ها ساخته نمی‌شود.

## 3. محدوده مرحله اول

### داخل محدوده

- ساختار Solution مطابق معماری قفل‌شده پروژه
- پوسته WinUI 3، راست‌به‌چپ، فارسی و مناسب وضوح 1366×768
- Design System پایه: رنگ، فاصله، تایپوگرافی، Light/Dark/High Contrast و تراکم
- راه‌اندازی اولیه کسب‌وکار، شعبه، انبار، واحد پول و کاربر مدیر
- کاربران، نقش‌ها و مجوزهای پایه
- تنظیمات و نگهداری امن اطلاعات حساس
- Audit Log، Security Log و Technical Log پایه
- دسته‌بندی چندسطحی با ایجاد، ویرایش، مرتب‌سازی، جابه‌جایی، ادغام، مخفی‌سازی و آرشیو
- واحد، تبدیل واحد، کالا، بارکد و وضعیت فعال/غیرفعال/آرشیو
- ورود دسته‌بندی، کالا، بارکد، قیمت و موجودی اولیه از Excel با پیش‌نمایش، اعتبارسنجی و Rollback
- انبار، موجودی اولیه، گردش موجودی و لایه‌های موجودی
- مشتری نقدی پیش‌فرض و ثبت سریع مشتری
- صندوق فروش سه‌مرحله‌ای: کالا و مشتری، پرداخت، تأیید
- پرداخت نقدی و کارت دستی
- شیفت صندوق پایه
- ثبت تراکنشی فروش، پرداخت، کاهش موجودی و سند حسابداری حداقلی
- پیش‌نمایش و چاپ رسید پایه
- راهنمای فارسی و Workflow Definition برای تمام صفحات این مرحله
- Shortcut Manager پایه و مسیر کامل کار با صفحه‌کلید در POS
- Backup محلی قابل اعتبارسنجی
- اسکلت Installer، Health Check و Update Manifest
- تست‌های Unit، Integration، Database و مسیرهای حیاتی UI

### خارج از محدوده این مرحله

- اتصال واقعی PC-POS و PSP
- پنل پیامک واقعی، باشگاه مشتریان و Automation
- خرید، تأمین، تولید، حقوق، لجستیک و فروشگاه آنلاین
- گزارش‌ساز پیشرفته و AI Local
- حسابداری و خزانه‌داری کامل
- Multi-company کامل و همگام‌سازی اینترنتی

برای موارد خارج از محدوده، فقط در صورت نیاز Contract پایدار تعریف می‌شود. برای نمونه، تنظیم اتصال پیامک در آینده باید با انتخاب ارائه‌دهنده، واردکردن API، شماره فرستنده و دکمه «آزمایش اتصال» انجام شود. API به‌صورت رمزگذاری‌شده ذخیره خواهد شد و جزئیات فنی به کاربر نمایش داده نمی‌شود. هیچ صفحه نمایشی، داده جعلی یا دکمه بدون عملکرد در Build عملیاتی وجود نخواهد داشت.

## 4. معماری

Solution این پروژه‌ها را خواهد داشت:

- `ERP.Domain`: موجودیت‌ها، Value Objectها، قواعد قطعی و Eventهای دامنه؛ بدون وابستگی به UI یا دیتابیس.
- `ERP.Application`: Use Caseها، قراردادهای Repository، اعتبارسنجی، مجوزها و مرز تراکنش.
- `ERP.Infrastructure`: زمان، رمزنگاری، فایل، Logging و سرویس‌های عمومی سیستم‌عامل.
- `ERP.Persistence`: Firebird، Migrationها، Unit of Work و پیاده‌سازی Repositoryها.
- `ERP.Desktop`: WinUI 3، View، ViewModel، Navigation و Design System.
- `ERP.LocalAgent`: قرارداد و Host پایه برای چاپ، Backup، Device و کارهای پس‌زمینه.
- `ERP.Reporting`: قرارداد داده گزارش‌پذیر برای قابلیت‌های مرحله اول.
- `ERP.Integrations`: قرارداد Adapterها و Outbox؛ بدون اتصال واقعی خارج از محدوده.
- `ERP.ImportExport`: خواندن فایل، نگاشت ستون‌ها، اعتبارسنجی، Import Batch و Rollback.
- `ERP.Sync`: قرارداد Inbox/Outbox و Idempotency برای توسعه آینده.
- `ERP.AI`: قرارداد Help/Tutor؛ بدون بارگذاری مدل در این مرحله.
- `ERP.Tests`: تست‌های مشترک و ابزارهای تست؛ تست‌های نزدیک به هر پروژه نیز مجازند.

وابستگی‌ها همیشه به سمت هسته هستند. `Domain` به هیچ پروژه دیگری وابسته نیست. UI هیچ قانون مالی یا انباری را در Code-behind نگه نمی‌دارد.

## 7. پول، تاریخ و متن فارسی

- مقدار مرجع پول در دیتابیس «ریال» و عدد صحیح است تا ابهام و خطای اعشاری ایجاد نشود.
- نمایش پیش‌فرض «تومان» است و کاربر می‌تواند واحد نمایشی را تغییر دهد.
- تبدیل تومان و ریال فقط در Value Object و Formatter مرکزی انجام می‌شود.
- زمان در دیتابیس به شکل استاندارد و قابل پردازش ذخیره می‌شود؛ نمایش UI شمسی است.
- اعداد و جداکننده هزارگان در UI فارسی و خوانا هستند.
- متن‌های UI در Resourceهای متمرکز قرار می‌گیرند تا غلط املایی و متن پراکنده کاهش یابد.

## 8. جریان فروش

### مرحله 1: مشتری و کالا

- مشتری نقدی از ابتدا انتخاب شده است.
- اسکن بارکد بدون Focus دستی کالا را به سبد اضافه می‌کند.
- جستجو با نام، SKU، بارکد و Alias انجام می‌شود.
- تعداد با صفحه‌کلید یا دکمه‌های لمسی تغییر می‌کند.
- فقط اطلاعات لازم سبد نمایش داده می‌شود.

### مرحله 2: پرداخت

- روش نقدی یا کارت دستی انتخاب می‌شود.
- مجموع پرداخت باید با مبلغ قابل پرداخت برابر باشد، مگر فروش اعتباری بعداً با مجوز اضافه شود.
- ارسال دوباره فرمان، پرداخت تکراری ایجاد نمی‌کند.

### مرحله 3: تأیید

- خلاصه مشتری، اقلام، تخفیف و پرداخت نمایش داده می‌شود.
- «ثبت و چاپ» تراکنش واحدی را اجرا می‌کند.
- ثبت Sale، Payment، Stock Movement و Journal Entry یا همگی موفق می‌شوند یا همگی Rollback می‌شوند.
- بعد از موفقیت، کاربر می‌تواند رسید را چاپ کند یا فروش جدید را شروع کند.

## 9. تجربه کاربری

- هر صفحه یک مأموریت و یک دکمه اصلی دارد.
- پیام خطا ساده و فارسی است و جزئیات فنی فقط در بخش پشتیبانی دیده می‌شود.
- فرم‌ها مقدار پیش‌فرض امن دارند و اطلاعات تکراری را از کاربر نمی‌گیرند.
- هنگام ثبت کالا، دسته‌بندی همان‌جا قابل جستجو و ایجاد سریع است و کاربر مجبور به ترک فرم نمی‌شود.
- عملیات پرتکرار با صفحه‌کلید کامل می‌شوند.
- حذف داده‌های قابل حذف دو تأیید دارد؛ اسناد فروش ثبت‌شده فقط Void/Reverse می‌شوند.
- تنظیمات Integrationها به شکل Wizard کوتاه طراحی می‌شوند؛ کاربر نیازی به Connection String، Header یا JSON ندارد.
- Loading، Empty، Error و Success State برای هر صفحه تعریف می‌شود.

## 10. امنیت و مجوز

- مدیر اولیه در راه‌اندازی ساخته می‌شود و رمز عبور Hash می‌شود.
- API Key و Secretها با Windows Data Protection و Scope مناسب دستگاه/کاربر رمزگذاری می‌شوند.
- هر Use Case حساس مجوز را در Application Layer بررسی می‌کند؛ مخفی‌کردن دکمه به‌تنهایی امنیت محسوب نمی‌شود.
- تغییر قیمت، تغییر موجودی، Override و عملیات امنیتی Audit می‌شوند.
- اطلاعات فنی و Secretها وارد Log نمی‌شوند.

## 11. پایداری و کارایی

- Queryهای لیست صفحه‌بندی می‌شوند و Gridها Virtualization دارند.
- Projection موجودی برای نمایش سریع استفاده می‌شود، ولی Stock Movement مرجع حقیقت است.
- عملیات پس‌زمینه در زمان کار POS اولویت پایین‌تری دارد.
- هدف Queryهای روزمره کمتر از 200ms و ثبت فروش محلی کمتر از 500ms است.
- Migrationها نسخه‌دار، تکرارپذیر و قابل بازیابی هستند.
- Outbox در همان تراکنش تجاری ثبت می‌شود تا رخدادها از بین نروند.

## 12. خطا و بازیابی

- خطاهای Validation کنار فیلد و به فارسی نمایش داده می‌شوند.
- خطاهای زیرساخت با Correlation ID ثبت می‌شوند و پیام ساده دارند.
- قطع چاپ باعث تکرار ثبت فروش نمی‌شود؛ فروش ثبت می‌شود و چاپ قابلیت Retry دارد.
- شکست Migration یا Update برنامه را به نسخه سالم قبلی برمی‌گرداند.
- Backup فقط زمانی سالم محسوب می‌شود که بازخوانی و بررسی ساختاری آن موفق باشد.

## 13. تست و کنترل کیفیت

برای هر قابلیت، تست قبل یا هم‌زمان با پیاده‌سازی نوشته می‌شود:

- Unit Test برای Money، تبدیل واحد، قواعد قیمت، موجودی، مجوز و State Machineها
- Integration Test با دیتابیس Firebird موقت برای Repository و تراکنش فروش
- Migration Test از دیتابیس خالی و نسخه قبلی
- UI/ViewModel Test برای Navigation، Validation و Shortcutها
- سناریوی خودکار حیاتی: ساخت کالا، موجودی اولیه، شروع شیفت، فروش نقدی، کاهش موجودی و چاپ مجدد
- تست Rollback با ایجاد خطای عمدی در میانه ثبت فروش
- تست Idempotency برای ثبت دوباره فرمان فروش
- تست Performance با داده نمونه حجیم و ثبت زمان واقعی
- بررسی دستی RTL، متن فارسی، وضوح 1366×768، Keyboard-only و Touch targetها

هیچ بخش Done نیست مگر تست‌های مرتبط موفق باشند و Help/Permission/Audit آن تکمیل شده باشد.

## 15. معیار پذیرش مرحله اول

مرحله اول زمانی کامل است که روی یک سیستم تمیز ویندوزی بتوان:

1. برنامه را نصب و راه‌اندازی کرد.
2. مدیر، فروشگاه، شعبه و انبار را بدون تنظیم فنی ساخت.
3. کالا را با بارکد و موجودی اولیه ثبت کرد.
4. فایل Excel کالا، بارکد، قیمت و موجودی را پیش‌نمایش و با گزارش خطای فارسی وارد کرد و در صورت نیاز کل Import Batch را Rollback کرد.
5. شیفت صندوق را شروع کرد.
6. فروش نقدی یا کارت دستی را در سه مرحله ثبت کرد.
7. مشاهده کرد که موجودی، پرداخت و سند حسابداری حداقلی هماهنگ ثبت شده‌اند.
8. رسید را پیش‌نمایش، چاپ و بدون تکرار فروش مجدداً چاپ کرد.
9. عملیات اصلی را فقط با صفحه‌کلید انجام داد.
10. از هر صفحه راهنمای فارسی همان صفحه را باز کرد.
11. Backup معتبر گرفت، بازیابی آزمایشی انجام داد و سلامت سیستم را مشاهده کرد.
12. تمام تست‌های خودکار و بررسی‌های کیفی این مرحله را با موفقیت گذراند.

## 16. فرض‌های اجرایی

- اولین استقرار تک‌سیستم و Firebird Embedded است؛ طراحی Connection Factory برای Firebird Server در LAN آماده می‌ماند.
- Build آزمایشی از نظر قابلیت‌های داخل محدوده Production-grade است و فقط روش استقرار آن کنترل‌شده و موازی با سیستم فعلی است.
- واحد نمایشی پیش‌فرض تومان است.
- مشتری نقدی و یک شعبه/انبار پیش‌فرض هنگام راه‌اندازی ایجاد می‌شوند.
- چاپگر واقعی برای توسعه اجباری نیست؛ Print Preview و Adapter آزمایشی مسیر را پوشش می‌دهند.
- سرویس‌های بیرونی مانند SMS و PC-POS تا زمان انتخاب Provider با Fake Adapter تست می‌شوند.
- تغییر این فرض‌ها بعداً از مسیر Change Request انجام می‌شود.
